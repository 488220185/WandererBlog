## 流浪者博客：技术博客从零搭建 + SEO 改造

**线上地址**：https://dev-notes-blog-23897.app.workbuddy.host/
**应用 ID**：`wbapp_D2sZRRlKM1e4roUd642xwo`

### 技术选型
Next.js 15.5.4（App Router）+ React 19 + Tailwind 3 + TypeScript
云后端：WorkBuddy 云服务（数据库 / 认证 / 存储），SDK 为 `@tencent-ai/workbuddy-cloud-sdk@dev`

### 数据库结构
- `posts`：`id / owner_id / title / slug(unique) / excerpt / content_md / cover_url / tags(text[]) / status / views / reading_minutes / created_at / updated_at`
- `site_owner`：单行表（`id=1`），记录站点归属与标题/副标题/作者简介。首个注册用户自动成为博主，可编辑全部文章
- 函数 `bump_post_view(text)`：SECURITY DEFINER，匿名可调用的浏览量自增

### ⚠️ 重要坑：auth.uid() 未登录时返回字符串 'anon' 而非 NULL
RLS 策略若写成 `owner_id = auth.uid()`，匿名访客会匹配上 `owner_id='anon'`，**任何人都能写入文章表**。
修法：建 `is_signed_in()` 函数判断 `auth.uid() IS NOT NULL AND <> '' AND <> 'anon'`，所有写策略都要带上它。
这是本次实测发现并修复的真实安全漏洞。

### SEO 改造要点（客户端渲染 → 服务端渲染）
原架构下文章列表是客户端组件异步取数，爬虫抓到的是空 HTML，一篇都收录不到。改造做法：
- 数据层拆分：`lib/api-server.ts`（RSC 读，服务端匿名只读已发布）+ `lib/api.ts`（客户端写/鉴权操作）
- `lib/markdown-server.ts` 用 unified 服务端把 Markdown 转 HTML，保证爬虫读到全文
- 搜索/分页从 useState 改为 URL 参数（`?tag=&q=&page=`），URL 可分享可爬取
- `app/robots.ts` + `app/sitemap.ts` 自动生成（sitemap 含 18 条：3 固定页 + 4 文章 + 11 标签）
- 每页 `generateMetadata`，文章页输出 `BlogPosting` JSON-LD
- 详情页加上一篇/下一篇导航，为爬虫提供站内爬取路径

### 品牌名
统一收敛到 `lib/brand.ts`（SITE_NAME / SITE_SUBTITLE / SITE_URL），改博客名只改这一个文件。

### 本地验证
`node scripts/verify-cloud.mjs` 可跑云服务关键路径检查（匿名读/写拒绝/标签聚合/RPC/会话）。
注意：云服务要求 Origin 精确匹配，**本地 localhost 无法正常访问数据面**，必须在发布后的真实域名上验证。

### 环境注意
- `npm run build` 需要 `dangerouslyDisableSandbox`，否则写 `.next/trace` 报 EPERM
- agent-browser 在这台机器上启动守护进程会被 SIGTERM 拦截，改用 curl 验证
- 发布器扫 package.json 判定是否依赖外部数据库，**装了 pg 驱动会被直接拒绝发布**（即使代码没用到）。导入脚本已改为零依赖的 REST 调用
- 发布后立刻验证偶发 000/超时，是冷启动抖动，等几秒重测即可

## 追加：绑定独立域名（方案 B）→ Vercel 自部署改造

### 结论：平台不支持绑定自定义域名
- 发布工具只有 `domainPrefix`（子域名前缀），无自定义域名参数，且创建时固定不可改
- 官方文档 Overview / Results 全文未提及域名绑定
- **更硬的障碍**：云服务对 Origin 做精确匹配，域名一换，登录直接失效

### 已完成的改造（让项目能在 Vercel + 自有域名跑）
1. **数据已导出**：`seed/posts.json`（4 篇文章，含完整 Markdown）
2. **后端适配层** `lib/backend.ts`：通过 `NEXT_PUBLIC_BACKEND` 切换 workbuddy / supabase
   - `lib/cloud.ts` 改成 Proxy，把方法调用转发到适配层，业务代码零改动
   - Supabase 侧把 auth 包成与 WorkBuddy 一致的调用形状
   - **踩坑**：backend.ts 不能 import cloud.ts（循环依赖），WorkBuddy 实例在 backend.ts 内直接创建
3. **Supabase 资产**：`supabase/schema.sql`（建表+函数）、`supabase/rls.sql`（策略，同样带 is_signed_in()）
4. **部署配置**：`vercel.json`、`.env.example`、`README.md` 完整六步部署指南
5. `SITE_URL` 改为读 `NEXT_PUBLIC_SITE_URL` 环境变量，换域名只需改环境变量

### 已知限制
- Supabase 后端**未接入文件存储**（图片/附件上传会提示"当前后端未启用文件存储"）。要支持需再实现 Supabase Storage 适配
- Supabase 后端**无微信登录**（微信是 WorkBuddy 平台能力）
- 本地 localhost 无法访问 WorkBuddy 数据面（Origin 校验），验证要用线上域名或改用 Supabase 后端

### ⚠️ Supabase 已改密钥体系（2026年新变化，重要）
Supabase 正在弃用 anon / service_role，改用：
- **publishable key**（`sb_publishable_...`）→ 替代 anon，可公开，客户端用
- **secret key**（`sb_secret_...`）→ 替代 service_role，绕过 RLS，服务端用
- 旧 JWT key（`eyJ...`）2026 年底前弃用，但目前仍可用

**关键坑：新式 secret key 不能放 `Authorization: Bearer` 头**，平台会按 JWT 解析并报 `Invalid JWT`。必须只走 `apikey` 头。
导入脚本已做兼容（按 `eyJ` 前缀判断格式），客户端同时兼容 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 和 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` 两个变量名。
